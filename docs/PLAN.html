Motor claims FNOL agent on Azure: the plan

From where we are to "it runs end to end in Azure", then what comes after. Last updated 8 Oct 2026. This page is updated as each tier finishes; the change log is at the bottom.

In one line: build the agent, prove it on your Mac against the 29 scenarios, then deploy it to Azure on the free tier and walk through every resource yourself.

FNOL = first notice of loss: the moment a policyholder first tells the insurer something happened ("a bus hit my car"). The agent registers the claim, gives a reference, answers status questions, and pays small payouts; anything bigger, or anyone hurt, goes to a person.

Goal of Phase 1: you open a public URL, sign in as a test policyholder, report a collision, get a claim reference, and then see that conversation's trace in App Insights and the model call in APIM. Phase 2 holds everything that makes it better but isn't needed to get there.

Can it be tested on the Mac?

Mostly yes. The agent's behaviour is tested locally first, so when something fails in Azure it is the wiring, not the agent. Only the Azure-managed services need Azure.

Tier 1 · The FNOL agent passes the gates on your Mac

Done · 9 Oct

No real model, no cost: a scripted model plays the agent's side.

  • The agent's own parts: intents learned from the spec's example messages; refusal texts; the "never promise cover" wording; claim-status answers with no model call
  • The payout rule: ₹25,000 read from the spec, held by a table test
  • The claims system: a small MCP server on PostgreSQL implementing the spec's operations; refusals come back with a reason type (declined or temporary); each policyholder sees only their own claims
  • The local composition: harness + these parts + the simulated world
  • Every gate failure routed to the spec it came from, not patched in the agent alone
Done when: all four gates (behaviour, features, structure, harness) pass against the 29 motor-claims scenarios.

Result: ✅ behaviour 29/29 · features 64/64 statements (286 tests) · structure 16/16 layers · harness 54 proved, 23 accepted gaps with reasons, 4 not applicable. The shared library is ~84% of what this agent runs, and none of it had to be edited. 16 findings, listed in FINDINGS.md. The most important: ~1,110 lines of shared mechanism had to be copied, not imported (moving them into the library would take reuse to ~90%). Another made a scenario pass for the wrong reason; that is now caught.

Phase 2: after it runs in Azure

In the order I'd do them. Each one is measured against what Phase 1's real traffic shows.

Tier 6 · Router lanes

Phase 2

Send each message to the cheapest path that can answer it safely: fixed flow (code answers), RAG (answers from documents), or agent (several dependent steps).

  • ~500 labelled motor-claims messages (a model proposes labels, a person approves)
  • Local classifier (Model2Vec + scikit-learn, ~1 ms, no network call) as router layer 2
  • A small LLM as layer 3, only when the classifier is unsure or there are several asks
  • Release gate: accuracy per route, and complex questions never sent to a fixed flow

Tier 7 · RAG over policy wording

Phase 2
  • Sample motor policy wordings embedded into pgvector (same PostgreSQL)
  • Answers only from retrieved clauses, cited; still no promise of cover
  • Entitlement filter first: only the policyholder's own policy wording
  • New scenarios: cited answer, clause not found, a planted instruction inside a document

Tier 8 · Several asks, the full design

Phase 2
  • The sorting step returns each ask with its part of the message; the parts must cover the whole message
  • Read-only parts in parallel; parts that change something run one at a time, each confirmed
  • A key per part (message id + part number), so a retry repeats nothing
  • One reply, reporting each part's own success or failure; more than three asks: ask which first

Tier 9 · Cost calculation

Phase 2
  • Cost per conversation and per outcome (claim registered, payout made) from real traces
  • Share of messages per lane: fixed flow / RAG / agent, measured, not assumed
  • Hybrid vs all-agent comparison with the measured shares (deck slide 128)
  • A workbook in Azure Monitor; budget thresholds from App Configuration

Tier 10 · Chatwoot and production shape

Phase 2
  • Chatwoot desk on Container Apps (our chat window in front; Chatwoot for the staff inbox and hand-offs), with webhook dedupe
  • Service Bus turn queue, outbox, Web PubSub: closed tabs and restarts never lose a turn
  • Teams cards for handlers; Content Safety at the edge
  • Foundry models behind APIM; Entra External ID for policyholders
  • Costed first: Chatwoot and Service Bus are where the free tier likely ends

Tier 11 · Library clean-up from the second agent

Phase 2

What building FNOL showed the shared library still lacks (FINDINGS.md):

  • Move the copied mechanism into agent_harness: the approval-backed action tool, turn orchestration, scenario wiring (F-2, F-3, F-15). Reuse would go from ~84% to ~90%.
  • Remove the clothing words still in the library: scopes, defaults, order_id (F-14)
  • Make it possible to extend: redaction patterns, the session field name, created references kept in the trace, judging per clause (F-4, F-5, F-8, F-10)
  • Spec gaps: refusal vs handoff order, registration plate as "a named policy" (F-6, F-7)

Words used here

GatesThe four automatic checks every build must pass: behaviour (the scenarios), features (every promise in the spec has a test), structure (every layer exists), harness (every required capability is proved or knowingly accepted as a gap).
AOASThe agent's spec file: what it may do, must refuse, and when it hands over to a person.
Fixed flow / RAG / agentCode answers / answers from retrieved documents / a model works through several dependent steps.
APIMAzure API Management: the one door every model call goes through, with limits and token counts.
DBOSA library that makes a wait (e.g. for a handler's approval) survive restarts, storing its state in PostgreSQL.
Container AppsWhere our containers run; scales to zero, so idle costs nothing.
